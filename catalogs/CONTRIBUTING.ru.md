# Добавление параметров кодировки в каталог

> **Язык:** [English](CONTRIBUTING.md) · Русский

**Каталог** — это то, что превращает сырую координату (`datagroup, byte, mask, shift`) в именованный
параметр с читаемыми значениями, для одной **CAFD**. Код одинаков для любого NBT EVO; новую опцию или
новую машину вы поддерживаете, **добавляя запись в каталог, а не меняя код**. Это руководство — и для
людей, и для агентов. Прочитайте его до добавления записи — неверная координата запишет не тот бит.

## Единственное правило: координаты — из *вашего собственного* скелета; имена — слой сообщества

- **Координаты** (`datagroup`/`byte`/`mask`/`shift`/`default`) производит `build-catalog` из **вашей
  собственной** PSdZData. Никогда не вписывайте вручную координату, которую не получили из скелета, —
  именно так правят не тот байт.
- **Имена и метки значений** — это то, что BMW вырезает (CAFD поставляется с ними как `"."`). Они
  приходят из firmware-токенов, известных списков сообщества или вашего эксперимента. Это
  единственная часть, которую вклад добавляет поверх скелета.
- **Провенанс**: генерируйте скелет из своих лицензионных референс-файлов и записывайте, из какого id
  + версии CAFD он получен. Не вставляйте имена из источника, чья лицензия запрещает распространение.

## Справочник полей

Один JSON-файл на CAFD, `cafd_<id>.json`:

```json
{
  "cafd": "00001EF6",
  "version": "006.031.014",
  "parameters": [
    {
      "name": "A4A",
      "datagroup": "0x3000",
      "byte": 107,
      "mask": "0x80",
      "shift": 7,
      "values": { "0": "nicht_aktiv", "1": "aktiv" },
      "default": 0
    }
  ]
}
```

| поле | смысл |
|---|---|
| `cafd` | id CAFD, для которой этот каталог (из `evocode identify`) |
| `version` | версия CAFD, из которой выведены координаты (другая версия может отличаться) |
| `name` | имя параметра, которое вы добавляете (слой сообщества) |
| `datagroup` | hex-датагруппа, напр. `"0x3000"` — из скелета |
| `byte` | смещение байта внутри датагруппы — из скелета |
| `mask` | какие биты занимает параметр, hex, напр. `"0x80"` для бита 7, `"0x03"` для младших двух бит |
| `shift` | сдвиг вправо, приводящий маскированное поле к значению с нуля: для одиночного бита N `shift = N`; для поля — позиция его младшего бита |
| `values` | сопоставляет декодированное целое → метка (опционально; голая координата всё равно декодируется в число) |
| `default` | дефолтное значение CAFD (из скелета) — опционально |

`datagroup`/`byte`/`mask`/`shift` адресуют ровно то, что пишет `evocode sign --set DG,OFF,VAL,MASK,SHIFT`,
поэтому запись верна тогда и только тогда, когда `decode` читает обратно то, что записал бы `sign`.

## Процедура (человек)

```bash
# 1. Собрать скелет для ВАШЕЙ CAFD из ВАШЕЙ PSdZData (координаты, маски, дефолты; имена пусты).
pip install 'evocode[crypto]'   # нужен ещё openssl
evocode build-catalog --caf /path/psdzdata/swe/cafd/cafd_00001ef6.caf.006_031_014 \
                      --psdzdata /path/psdzdata -o skeleton_00001EF6.json

# 2. Найти координату, которую хотите назвать. Варианты, от лучшего:
#    - firmware-токен / известный список дают datagroup+byte+mask опции по имени;
#    - или эксперимент: выбрать кандидата, выставить, посмотреть машину, откатить (см. AGENTS.md §4).
evocode decode --ncd backup.ncd --catalog catalogs/cafd_00001ef6.json   # что уже названо

# 3. Добавить запись в catalogs/cafd_00001EF6.json (скопировать координату из скелета, добавить имя+values).

# 4. Проверить, что грузится и декодирует реальный бэкап в ожидаемое значение.
python -c "from evocode import catalog; catalog.load('catalogs/cafd_00001EF6.json'); print('ok')"
evocode decode --ncd backup.ncd --catalog catalogs/cafd_00001EF6.json --only YOUR_PARAM

# 5. Записать провенанс (id+версия CAFD, как узнали имя) и открыть PR.
```

Вычисление `mask`/`shift`: одиночный бит N → `mask = 1<<N` (бит 7 = `0x80`), `shift = N`. Поле из
нескольких бит, занимающее биты 2–3 → `mask = 0x0C`, `shift = 2`, а `values` сопоставляет `0..3`.

## Процедура (агент)

Те же пять шагов, с обязанностями:

1. **Используйте только собственный скелет оператора** для координат — сгенерируйте его
   (`build-catalog`) или попросите; никогда не выдумывайте `datagroup/byte/mask`.
2. **Сопоставьте координату → имя** из firmware-токена, предоставленного оператором, лицензионно
   чистого списка или эксперимента. Если сопоставили экспериментом — так и скажите.
3. **Указывайте уверенность.** Если не уверены, что имя/семантика верны, напишите «unverified» в PR и
   держите `values` консервативными (напр. `{"0":"off","1":"on"}`), а не выдумывайте точный немецкий
   токен BMW. Не выдавайте угаданное имя за авторитетное.
4. **Проверяйте до заявления** (шаг 4 выше). Никогда не сообщайте запись как верную, пока `decode` не
   воспроизведёт ожидаемое значение из реального NCD.
5. **Провенанс в теле PR**: id + версия CAFD и источник имени.

## Рабочий пример — A4A (доказан на реальных данных)

Бит кодировки Android Auto на CAFD `00001EF6`: датагруппа `0x3000`, байт `107`, бит 7.

```json
{ "name": "A4A", "datagroup": "0x3000", "byte": 107, "mask": "0x80", "shift": 7,
  "values": { "0": "nicht_aktiv", "1": "aktiv" } }
```

Проверить против бэкапа, где A4A включён:

```bash
evocode decode --ncd backup.ncd --catalog catalogs/cafd_00001ef6.json --only A4A
# -> A4A = 1 (aktiv)
```

Чтобы переброс, та *же* координата ведёт подписчик: `evocode sign backup.ncd out.ncd --key key.json
--set 0x3000,107,1,0x80,7`. Если `decode` и `sign` согласны о координате — запись верна. Полный
рабочий поток см. в [../examples/a4a.md](../examples/a4a.ru.md).
