# Root-доступ (OPT_DEBUG) — осуществимость и дизайн

> **Язык:** [English](root-access.md) · Русский

**Короткий ответ: да, включение root/SSH ложится в проект чисто** — это *тот же транспорт и тот же
ключ*, что инструментарий уже использует для кодировки и FSC. Это **не** SSH-операция и не
предполагает SSH; это флеш по диагностической плоскости, который *производит* SSH. Хореография
SWDL file-copy реализована в ``swdl.py``; правка OPT_DEBUG и CLI — в ``root.py`` / ``cli.py``.

## Что значит «root-доступ» на NBT EVO

У головного устройства есть dev-интерфейс — SSH (22), telnet (23), qconn (8000), — который поднимается
как **root** по OBD/ENET. На стоковом устройстве он выключен. Он управляется одной настройкой в
стартовом конфиге устройства, `/fs/sda0/opt/sys/etc/starter.cfg`: сервис **OPT_DEBUG**,
поставляемый как `STOP`, переключается в `RUN`. Включите его, перезагрузитесь — и dev-порты открыты.

Это и есть root, нужный для шагов замены файлов прошивки в других частях проекта — установки
blobB-пропатченного `NBTCarHU` (FSC owner-CA) или афтермаркет-плагина. См. модель двух плоскостей в
[../AGENTS.md](../AGENTS.ru.md) (§1): кодировка и FSC идут по диагностической плоскости и SSH им не
нужен; нужен он только для заливки *файлов* на разделы устройства — и OPT_DEBUG открывает эту
возможность.

## Почему для начала SSH не нужен

Включение OPT_DEBUG — это **флеш по диагностическому каналу**, по форме идентичный тому, что evocode
уже делает:

```
ENET → HSFZ (TCP 6801) → вход во флеш-загрузчик
   → UDS SecurityAccess 0x27 Level 3  (BMWSigVerify: подписать seed ключом L3 оператора)
   → SWDL «no-signature file-copy» (LIVE-DIRECT) пропатченного starter.cfg  (OPT_DEBUG STOP→RUN)
   → finalize → перезагрузка → sshd(22)/telnetd(23)/qconn(8000) как root
```

Контейнер «no-signature file-copy» пишет файл без записи подписи, поэтому проверка подписи SWDL к нему
не применяется — именно поэтому *пропатченный* конфиг вообще можно установить. SecurityAccess L3 — тот
же seed/key-поток, что у записи кодировки; ключ — **собственный** ключ машины оператора, который
evocode уже восстанавливает (`recover-key`, kind `l3`).

## На чём это стоит (всё уже есть в evocode)

| Нужно | Статус в evocode |
|---|---|
| Транспорт HSFZ, обнаружение | ✅ `hsfz.py` |
| UDS-сессия / SecurityAccess / рутины | ✅ `uds.py` |
| Подпись seed по L3 (BMWSigVerify, e=3) | ✅ `l3.py` |
| Восстановить L3-ключ оператора из его PSdZData | ✅ `keys.py` (`recover-key --kind l3`) |
| **Вход во флеш-загрузчик + хореография SWDL no-signature file-copy** | ✅ `swdl.py` |
| **Версионно-согласованный пропатченный `starter.cfg` из собственного флеша оператора** | ✅ `root.py` (`root prepare`) |

То есть возможность — это в основном *сборка уже существующих примитивов* плюс один новый модуль
(поток SWDL file-copy) и один шаг данных (произвести пропатченный `starter.cfg`).

## Жёсткое ограничение: согласовать версию конфига

`starter.cfg` **зависит от сборки**. Конфиг не той версии валит **следующую загрузку** (устройство
загружает `starter.cfg`; плохой оставляет его неспособным поднять HMI или загрузиться вообще).
Универсальные анлокеры инлайнят один конфиг (например, валидный для семейства NBT-EVO `007.xxx`) и
явно отказывают другим линиям — ровно та ловушка, которой проект избегает в остальном. Чистый,
провенанс-корректный способ, в духе `build-catalog` и `recover-key`:

- Взять сток `starter.cfg` с **собственного** устройства оператора (прочитать его) или из его
  **собственного** флеш-контейнера PSdZData под этот конкретный BTLD/SVK.
- Сделать минимальную правку `OPT_DEBUG STOP→RUN`, сохраняя длину в байтах, в *этом* файле.
- Установить через no-signature file-copy; сохранить нетронутый оригинал как откат.

Это устройство (для справки) — программная линия **006.016.002**, *не* из семейства `007.xxx`, на
которое целится универсальный анлокер, так что его инлайн-конфиг был бы не тем файлом. Конфиг должен
приходить из собственного флеша этого устройства.

## Риск и обратимость

- **Класс «кирпича»**: boot-config. Плохая запись валит следующую загрузку. Смягчение: версионная
  согласованность; dry-run; запуск записи **отсоединённо** (чтобы обрыв SSH/терминала её не порвал);
  сохранить сток-конфиг.
- **Обратимо**: перефлешить байт-в-байт сток `starter.cfg` тем же путём (`--revert`). Dev-интерфейс
  живёт независимо от HMI, так что даже устройство, которое не поднимает HMI, всё ещё достижимо для
  отката — *после того как OPT_DEBUG включён*. До этого SSH-подстраховки нет, только serial/eMMC.
  Самое первое включение — шаг наибольшего риска.
- **Ворота**: как у `write`/`fsc apply` — ворота согласия `NBTEVO_OWN_VIN`, dry-run по умолчанию,
  `--commit` заново сверяет VIN. Флеш дополнительно требует АКБ на зарядке.

## Использование

```bash
evocode root status  --host 169.254.199.99                 # включён ли OPT_DEBUG? открыты ли 22/23/8000?
evocode root prepare --starter-cfg stock.cfg -o patched.cfg # правка STOP→RUN + сохранить сток
evocode root enable  --host 169.254.199.99 --l3-key l3.json --starter-cfg stock.cfg  # DRY RUN
evocode root enable  --host 169.254.199.99 --l3-key l3.json --starter-cfg stock.cfg --commit
evocode root revert  --host 169.254.199.99 --l3-key l3.json --stock stock.cfg   # перефлешить сток cfg
```

`evocode/swdl.py` — вход во флеш-загрузчик + SWDL no-signature file-copy.
`evocode/root.py` — правка `starter.cfg` `STOP↔RUN` и сборка контейнера.
`root enable/revert` переиспользуют `hsfz`/`uds`/`l3`/`consent`.
