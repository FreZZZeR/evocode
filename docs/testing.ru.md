# Тестирование изменений без машины (IDEmu)

> **Язык:** [English](testing.md) · Русский

Часть изменений evocode можно отрепетировать в эмуляторе до того, как трогать живую голову.
[IDEmu](https://github.com/herrbimmer/IDEmu) — QEMU-эмулятор головы NBT EVO / iDrive6 (macOS), который
грузит **родной** софт устройства из вашей собственной PSdZData/SWFL; есть SSH и редактор кодировок.
(Лицензия: PolyForm Noncommercial.)

Реально полезен он здесь для одного — **свопа blobB-якоря**: убедиться, что пропатченный `NBTCarHU`
(`evocode fsc patch-blobb`) грузит родной софт устройства и **не кирпичит** его. Это самый страшный шаг
on-car FSC-процедуры.

## Что он может проверить, а что нет

| ✅ Репетируется в IDEmu | ❌ Только у машины |
|---|---|
| Пропатченный `NBTCarHU` грузит QNX (сервисы + SSH поднимаются) | Команды диагностической плоскости — `write`, `fsc apply`/`read`, `root` — IDEmu не выставляет HSFZ (TCP 6801) |
| Нет регрессии загрузки против стока (доходит до той же стадии) | Что FSC реально **принят** (это диагностическая запись + живой `NBTCarHU`) |
| Бинарь цел / патч length-preserving | Рендер HMI и активация фич — валидированы только для некоторых сборок HMI¹ |
| Кодировка цела (лежит в отдельном образе, своп blobB её не трогает) | Карты / навигация, Android Auto |

¹ Если вашей сборки HMI нет в валидированном наборе IDEmu, загрузка подвисает под конец (HMI не
финиширует), а `NBTCarHU` — гейтится за готовностью HMI — не стартует. Это ограничение эмулятора/версии,
а не вашего патча: системный слой (загрузка / SSH / кодировка) вы всё равно проверяете. Сравните патч со
стоком — если **оба** доходят до той же стадии, своп boot-safe.

## Репетиция свопа blobB

1. **Baseline (сток).** Соберите version-matched окружение из своей SWFL, сделайте cold-boot и снимите
   по SSH: `uname -a`, размер `NBTCarHU`, `pidin a | grep -i carhu` (какие процессы подняты) и до какой
   стадии дошла загрузка. Это отделяет «патч сломал» от «эмулятор так себя ведёт на моей версии».
2. **Соберите пропатченный бинарь** в evocode (length-preserving — меняются только 128 байт blobB):
   ```bash
   evocode fsc find-blobb NBTCarHU.stock      # офсет + fp текущего якоря (per-build — не хардкодить)
   evocode fsc patch-blobb NBTCarHU.stock --key owner.json --backup stock_blobB.bin -o NBTCarHU.patched
   ```
3. **Внедрите в образ.** Патч length-preserving, значит стоковые 128 байт якоря лежат в корневом образе
   окружения байт-в-байт — замените их на месте и сделайте **cold-boot** (корневой образ — RAM-диск,
   правки в работающем госте не переживут ребут):
   ```python
   img = bytearray(open(".../sda.img", "rb").read())
   old = open("stock_blobB.bin", "rb").read()        # из --backup выше
   new = open("owner_blobB.bin", "rb").read()        # ваш якорь (evocode fsc keygen --blobb)
   i = img.find(old)
   assert i >= 0 and img.find(old, i + 1) == -1, "якорь не найден / не уникален в образе"
   img[i:i + 128] = new
   open(".../sda.img", "wb").write(img)
   ```
   (Альтернатива, ближе к on-car шагу: `scp` пропатченного `NBTCarHU` в работающий гост и рестарт HMI —
   повторяет at-car rename-over, но это не cold-boot с диска.)
4. **Cold-boot** пропатченного образа и сверка с baseline.

## Pass / fail

| Проверка | PASS | FAIL |
|---|---|---|
| Cold-boot пропатченного образа | дошёл до стадии baseline, QNX + сервисы живы | паника / виснет **раньше** baseline |
| SSH в гост | отвечает; `uname` = QNX OMAP5 | нет сессии |
| Процесс `NBTCarHU` | есть в `pidin a`, не в цикле падений | отсутствует / crash-loop |
| Размер бинаря | не изменился (патч length-preserving) | изменился |
| Якорь в образе | fp вашего якоря (`evocode fsc fingerprint`) | стоковый / чужой fp |

**PASS** = своп якоря boot-safe → у машины рискуете только транспортом записи, не кирпичом.

## Что это покрывает, а что нет

Репетирует **установку файла прошивки** (что пропатченный `NBTCarHU` грузится). Не покрывает шаги
диагностической плоскости (`fsc apply`/`read`, кодировку `write`, `root enable` — HSFZ в эмуляторе нет),
верификацию фич, карты и Android Auto. Это остаётся на машину. См. [root-access.md](root-access.ru.md)
про файловую плоскость и [../AGENTS.md](../AGENTS.ru.md) §1 про модель двух плоскостей.

## Заметки

- Офсет blobB ищите через `evocode fsc find-blobb` — никогда не хардкодить; он разный по сборкам.
- Эмуляция одноядерная (TCG) и медленная; дайте загрузке идти в фоне, не поллите.
- Как поднять стенд (сборка IDEmu, своя version-matched SWFL + гвоздь версии, create/build/run, повадки
  консольного моста и что на каком стенде можно разрабатывать) — в [dev-stand.md](dev-stand.ru.md).
- Консольный **мост** IDEmu даёт шелл, но **не** прокидывает exec-stdin (проверено: `cat`-over-exec пишет
  0 байт), поэтому передачу файла `evocode fw` на нём не проверить — только хореографию (remount / бэкап /
  rename-over / chmod на живом QNX, через `fw --modern`). `fw install` сверяет размер файла на устройстве и
  прерывается при несовпадении, так что это ограничение — или оборванная передача — не установит пустой файл.
