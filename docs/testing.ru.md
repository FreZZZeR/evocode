# Тестирование изменений без машины (IDEmu)

> **Язык:** [English](testing.md) · Русский

Часть изменений evocode можно отрепетировать в эмуляторе до того, как трогать живую голову.
[IDEmu](https://github.com/herrbimmer/IDEmu) запускает родной софт BMW под QEMU из вашей собственной
PSdZData/SWFL. Upstream охватывает CIC и iDrive 5–8; для NBT EVO / iDrive 5/6 есть macOS и Linux/WSL,
живой HMI, SSH, редактор кодировок, виртуальные CAN/GPS и cluster/HUD.
(Лицензия: PolyForm Noncommercial.)

В evocode он полезен для репетиции **свопа blobB-якоря** (`evocode fsc patch-blobb`) и хореографии
установки `fw`, а также как стенд разработки HMI/плагинов. Успех в эмуляторе уменьшает неопределённость
для этой пары софт/профиль, но не доказывает безопасность изменения на реальном железе.

Сверено 2026-11-20 с upstream `main`
[`d03ecd84f363`](https://github.com/herrbimmer/IDEmu/tree/d03ecd84f363): точные профили шима 24-03
(`007_051_002`) и 18-03 (`006_017_006`) уже влиты; общий реестр multi-firmware из
[PR #16](https://github.com/herrbimmer/IDEmu/pull/16) открыт и не влит, head
[`d73b049`](https://github.com/FreZZZeR/IDEmu/commit/d73b049d8f69e146b08018e8204a516a9bb7b501), обновлён относительно main `d03ecd8`;
по проверке GitHub 2026-11-20 — `mergeable=true`, `clean`, конфликтов нет. Четыре `007` из реестра
заново собраны и cold-boot до живого HMI проверены на этой ветке; это не проверяет принятие FSC.
Для нашей `006_016_002` по-прежнему нет полного matching SWFL и валидированного профиля; соседняя
`006_017_006` не подтверждает совместимость её HMI/ABI плагина. Linux/WSL и новый boot 18-03
локально не повторяли. Поднятие и выбор профиля — в [dev-stand.md](dev-stand.ru.md);
исторические наблюдения загрузки/SSH ниже относятся к 2026-11-11.

## Что он может проверить, а что нет

| ✅ Репетируется в IDEmu | ❌ Только у машины |
|---|---|
| QNX/сервисы/SSH загружаются после замены `NBTCarHU` | Команды диагностической плоскости — `write`, `fsc apply`/`read`, `root` — IDEmu не выставляет HSFZ (TCP 6801) |
| Нет регрессии загрузки против стока; пропатченный `NBTCarHU` работает, если baseline его запускает | Что FSC реально **принят** живым устройством |
| Бинарь цел / патч length-preserving; кодировка цела в отдельном образе | Активация фич, BMW-навигация/маршруты, живой Android Auto / CarPlay |
| HMI/плагины на точном валидированном профиле; виртуальные CAN/GPS/cluster/HUD и композиция карты от хоста | Радио/медиа/аудио, USB и физические сети машины |

Несовпадение версии/профиля может оставить QNX/SSH живыми без запуска HMI или `NBTCarHU`. В нашем
стенде 2026-11-11 так было с `007_001_016`. Одинаковая стадия загрузки стока и патча тогда подтверждает
лишь отсутствие более ранней регрессии, **не** исполнение пропатченного бинаря. Карта от хоста — не
движок BMW-навигации и не проверяет картографический FSC `0120`.

## Репетиция свопа blobB

1. **Baseline (сток).** Соберите version-matched окружение из своей SWFL, сделайте cold-boot и снимите
   по SSH: `uname -a`, размер `NBTCarHU`, `pidin a | grep -i carhu` (какие процессы подняты) и до какой
   стадии дошла загрузка. Это отделяет «патч сломал» от «эмулятор так себя ведёт на моей версии».
2. **Соберите пропатченный бинарь** в evocode (length-preserving — меняются только 128 байт blobB):
   ```bash
   evocode fsc find-blobb NBTCarHU.stock      # офсет + fp текущего якоря (per-build — не хардкодить)
   evocode fsc patch-blobb NBTCarHU.stock --key owner.json --backup stock_blobB.bin -o NBTCarHU.patched
   ```
3. **Внедрите в образ.** Остановите эмулятор и используйте одноразовый образ (сброс — пересборка из SWFL).
   Патч length-preserving, значит стоковые 128 байт якоря лежат в корневом образе
   окружения байт-в-байт — замените их на месте и сделайте **cold-boot** (корневой образ — RAM-диск,
   правки в работающем госте не переживут ребут):
   ```python
   img = bytearray(open(".../sda.img", "rb").read())
   old = open("stock_blobB.bin", "rb").read()        # из --backup выше
   new = open("owner_blobB.bin", "rb").read()        # ваш якорь (evocode fsc keygen --blobb)
   i = img.find(old)
   assert i >= 0 and img.find(old, i + 1) == -1, "якорь не найден / не уникален в образе"
   img[i:i + 128] = new
   open(".../sda.img", "wb").write(img)
   ```
   `scp` не подходит для консольного моста (см. [dev-stand.md](dev-stand.ru.md) §4).
4. **Cold-boot** пропатченного образа и сверка с baseline.

## Pass / fail

| Проверка | PASS | FAIL |
|---|---|---|
| Cold-boot пропатченного образа | дошёл до стадии baseline, QNX + сервисы живы | паника / виснет **раньше** baseline |
| SSH в гост | отвечает; `uname` = QNX OMAP5 | нет сессии |
| Процесс `NBTCarHU` | есть в `pidin a`, не в цикле падений | отсутствует / crash-loop |
| Размер бинаря | не изменился (патч length-preserving) | изменился |
| Якорь в образе | fp вашего якоря (`evocode fsc fingerprint`) | стоковый / чужой fp |

**PASS** требует, чтобы пропатченный `NBTCarHU` работал в этом окружении как минимум не хуже стока.
Если baseline его не запускает, отметьте проверку как **не выполненную**. Это не доказательство
безопасной загрузки на машине или принятия FSC; сохраняйте бэкап и путь восстановления живой головы.

## Что это покрывает, а что нет

Репетирует **установку файла прошивки** (что пропатченный `NBTCarHU` грузится). Не покрывает шаги
диагностической плоскости (`fsc apply`/`read`, кодировку `write`, `root enable` — HSFZ в эмуляторе нет),
реальную верификацию фич/FSC, маршруты BMW и живой Android Auto. Это остаётся на машину. См. [root-access.md](root-access.ru.md)
про файловую плоскость и [../AGENTS.md](../AGENTS.ru.md) §1 про модель двух плоскостей.

## Заметки

- Офсет blobB ищите через `evocode fsc find-blobb` — никогда не хардкодить; он разный по сборкам.
- Эмуляция одноядерная (TCG) и медленная; дайте загрузке идти в фоне, не поллите.
- Как поднять стенд (сборка IDEmu, своя version-matched SWFL + точное совпадение профиля шима, create/build/run, повадки
  консольного моста и что на каком стенде можно разрабатывать) — в [dev-stand.md](dev-stand.ru.md).
- Консольный **мост** IDEmu даёт шелл, но **не** прокидывает exec-stdin (проверено: `cat`-over-exec пишет
  0 байт), поэтому передачу файла `evocode fw` на нём не проверить — только хореографию (remount / бэкап /
  rename-over / chmod на живом QNX, через `fw --modern`). `fw install` сверяет размер файла на устройстве и
  прерывается при несовпадении, так что это ограничение — или оборванная передача — не установит пустой файл.
